# VexRiscv 大幅改进所需的结构变化

工作区唯一容量上限为 **40,000,000,000 字节**。不恢复旧的 10 GB 清理目标，不改固定封装引脚、电气条件、接口周期或完整 I/O 时序覆盖。主目标仍是综合与自研 P&R 协同优化；150/200 MHz、通用显著优于原厂均未完成。

## 本次实测与限制

新的合格检查点为 **65.9 MHz**：setup +0.019 ns、hold +0.134 ns，setup/hold 零违例，其他原厂最终检查通过，已生成位流。相对 65.4 MHz 仅提高 **0.765%**，不是用户要求的巨大改进。没有执行原厂 P&R、使用开源器件数据库或上板。

可独立复现的连续流程从 65.4 MHz 自研检查点开始，重新捕获内部时序反馈、选择两处 LUT 输入置换、执行 CEC、验证自主路线、测量整棵负载树并完成最终 STA/编码，耗时 **452.406 秒**。这是增量优化完整流程，不是从 RTL 冷启动的耗时。2 个 LUT 的输入和真值表同步改变，4 棵数据路线改变；资源数量、所有单元位置、时钟树、I/O 与状态数量不变。CEC 覆盖 8,608 个原状态/硬输入/端口观察点。

- 结果：`results/vexriscv_pin_batch_summary_001/summary.json`
- 推荐检查点：`results/vexriscv_pin_batch_reproduction_001/qualified_replay_checkpoint.json`
- 全部阶段、计时、命令：`results/vexriscv_pin_batch_reproduction_001/manifest.json`
- 高频障碍分析：`results/vexriscv_frequency_barrier_001/qualified_analysis.json`

先前探索中，单独选择局部收益最大的 `ng_coopt_1047`，相应 wire+cell 改善约 1.121 ns，整机报告 Fmax 却仍为 65.432 MHz。联合处理最坏路径上的 `ng_coopt_968` 后，才达到报告 65.980 MHz、资格频率 65.9 MHz。批次选择现在按竞争关键路径选择互不冲突的输入置换，并累计 setup/hold 路径预算；局部收益不能直接当作整体收益。

时间审计没有找到此前探索的完整单调时钟文件。按捕获文件结束时间减实测捕获耗时，到最终验收文件结束时间重建，约 **3,666.135 秒**，超过一小时，因此明确记为失败。新 452.406 秒连续复现是独立实验，不能抹去原失败记录；两者网表和路线哈希完全相同。

## 需要同时解决多少条路径

分析器逐一核对了全部 **2,757 条已报告 setup 路径**及其全周期关系，保持当前单元、时钟、I/O 预算不变，仅计算提高目标频率后所需的延迟改善。它不是新频率的 STA 验收，也不覆盖未报告的替代路径。

| 目标 MHz | 需要改善的已报告路径 | 最坏路径需减少 ns | 前五个发射起点覆盖 |
|---:|---:|---:|---:|
| 80 | 133 | 2.656 | 119 |
| 90 | 383 | 4.044 | 357 |
| 100 | 685 | 5.156 | 642 |
| 150 | 1,705 | 8.489 | 1,424 |
| 200 | 2,003 | 10.156 | 1,545 |

最坏路径数据延迟约 15.089 ns：布线 11.473 ns、组合单元约 3.271 ns、C2Q 0.344 ns。最前面的两段分别为 3.352 ns 和 3.522 ns：RS2[2] 寄存器驱动宽 LUT 的选择输入，宽 LUT 输出再驱动 ALU 输入。这个宽 LUT 的输出有 45 个接收端。另一个竞争路径有 14 级逻辑，布线 9.121 ns、单元及 C2Q 5.894 ns，不能仅修第一条。

在 90 MHz 的需求集合中，前五个发射组覆盖约 93.2%。其中 `dataCache_1.io_mem_cmd_payload_uncached` 对应寄存器贡献 172 条；到 150 MHz 时贡献 1,152 条。其他主要起点涉及 `execute_RS2[2]`、`execute_RS2[25]` 和指令缓存返回数据。说明需要对多个控制/算术锥进行区域划分和联合重构，不能只处理一个最大扇出或一条最长线。

## 单靠数据布线优化不够

进行一个明确不可当作实现预测的理想化计算：所有已报告路径的数据布线延迟统一减少，其他单元、时钟、I/O 和约束贡献保持不变。

| 剩余数据布线延迟 | 已报告路径允许的理想化频率上限 MHz |
|---:|---:|
| 75% | 78.12 |
| 50% | 95.05 |
| 25% | 111.39 |
| 0% | 123.91 |

最后一行仍被一条寄存器到固定输出的路径限制：约 **3.934 ns 发射时钟插入 + 4.136 ns 单元/C2Q**，合计约 8.070 ns。寄存器间的公共时钟延迟通常可以抵消，外部输出路径不会同样抵消。这不是器件极限，也不意味着仅优化逻辑即可达到 150 MHz；必须同时改变合法的逻辑/寄存器打包或时钟实现。不能删除 I/O 评测来隐藏这个限制。

## 已拒绝的物理候选

| 候选 | 报告 Fmax MHz | 实际约束 | setup WNS ns | 结论 |
|---|---:|---:|---:|---|
| 失败混合打包的源端重接 | 63.298 | 65.2 MHz | −0.461 | 拒绝，仍有 2 个 setup 违例 |
| 把关键 LUT 改放同 ALU CFU 的槽位 7 | 58.211 | 65.4 MHz | −1.888 | 拒绝，7 个 setup 违例 |
| 单一 LUT 输入置换 | 65.432 | 65.4 MHz | +0.007 | 合格但无全局增益 |
| 两个竞争路径联合输入置换 | 65.980 | 65.9 MHz | +0.019 | 独立连续复现通过 |

源端重接保留旧树下游片段并重新连接新的源，加入实际接收端关键性后，局部改善约 0.350 ns；完整 STA 验证仍不足以闭合。不能因为同 CFU 或几何距离更短，就宣称延迟一定更低。

## 下一阶段的执行目标

将 **90 MHz 完整 I/O** 作为检验结构性变化是否有效的阶段门槛（相对当前约 +36.6%），最终 150/200 MHz 目标保持。90 MHz 是实验目标，不是承诺或已实现结果。

1. **按目标周期建立多锥联合问题。** 以全部关键端点需求选择相互竞争的发射组，而非只取最差路径或最大单边收益。首先覆盖上表的五组主要控制/算术锥，并保护其他端点 setup/hold。
2. **综合、宏打包与区域复制一起选择。** 扩展完整宽 LUT 宏复制到 ALU 普通输入，联合寄存器控制前沿复制、区域接收端分组、宽逻辑重分解与进位链边界布局。对新增状态执行初始化和逐拍归纳等价证明；不新增接口周期。当前复制器对普通 LUT/宽宏/ALU 的支持仍分散，尚未实现这一统一优化器。
3. **用真实负载树反馈驱动布局与协商布线。** 将新输入负载、所有输出分支、局部拥塞及 setup/hold 剩余预算带入区域候选；移动宏或解除冻结后，同样保护未改逻辑的网络。现有几何距离和空载 PIP 估计只用于搜索，不能作验收。
4. **把输出时钟路径纳入同一目标。** 研究固定引脚下分区时钟和合法输出寄存器/逻辑打包。仅在等价、初态和周期证明成立时做寄存器边界移动，同时重新检查输入 hold、恢复/移除和脉宽；不能用统一提前时钟或放松 I/O 约束替代优化。
5. **同条件验收和消融。** 比较综合变化、物理变化和联合变化；均须在一个共享的一小时截止时间内完成 CEC、连通/配置审计、全部 I/O STA 和导出。拒绝超过预算、仅局部有效或全局退化的候选。原厂参考仍单列；已有 66.109/73.209 MHz 报告不是严格同网表同约束的当前最高合格基线，不据此宣称胜过原厂。

## 复现

```powershell
runtime_bundle/python/python.exe scripts/run_ownpr_pin_batch.py --report results/vexriscv_carry_neighbors_001/qualified_replay_checkpoint.json --target-mhz 65.9 --window 1 --count 2 --seconds 1200 --out results/<新的输出目录>
```

该入口从重新捕获开始共享一个截止时间，超时终止其子进程树；保存命令、来源哈希、独立候选和资格检查点。冻结 ZIP 与原合格结果不变。新增诊断、窗口选择及源端片段连接的针对性检查共 7 项通过；此前 pin/budget 相关 17 项与 source-reconnect 相关 27 项的日志分别保留，不能把它们当作本次重新运行的总数。新增测试最初有模块导入路径错误，修正后通过，失败日志保留。
